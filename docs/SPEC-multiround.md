# 多轮优化交互规范（SPEC）

> 目标读者：本插件的实现者。每条要求都写成可判定真假的形式，
> 标「**契约**」的是硬要求，标「**建议**」的是实现自由度较大的部分。
>
> 范围：多轮优化流程、继续方向、版本历史、**回退**、结果可编辑、
> 加入输入框、临时保存。

---

## 0. 术语

| 术语 | 含义 |
| --- | --- |
| 轮次 Round | 一次完整的「优化 → 出方向 → 等待选择」循环 |
| 版本 Version | 某一轮的优化结果，**只追加、不可修改、不可删除** |
| 方向 Direction | 本轮结束后给出的 3 个继续优化选项之一 |
| 基线 Base | 下一轮优化时喂给模型的内容 |
| 回退 Rollback | 把「当前基线」切到某个历史版本。**只换选中项，不删任何版本** |

---

## 1. 数据模型

```ts
type Version = {
  id: string;            // v1, v2, ... 单调递增
  round: number;         // 1-based
  /** 本轮基于哪一版继续；首轮为 null */
  baseId: string | null;
  /** 触发本轮的方向文案；首轮为 null */
  direction: string | null;
  /** 模型原始输出，永不修改 */
  raw: string;
  /** 用户编辑后的内容；未编辑时等于 raw */
  edited: string;
  createdAt: number;
  /** 这一版是从哪一版回退后重新分出来的；正常顺延为 null */
  rolledBackFrom?: string | null;
};

type MultiRoundState = {
  versions: Version[];         // 只追加（append-only）
  activeId: string | null;     // 当前展示/操作的版本
  /** 当前基线版本；回退改的就是它 */
  cursorId: string | null;
  phase: 'idle' | 'running' | 'awaiting' | 'failed';
  directions: string[];        // 长度 3，本轮给出的方向
  historyOpen: boolean;        // 历史面板是否展开
  error: string | null;
};
```

**契约 C1**：`versions` 只能 `push`。任何操作不得修改已有元素的 `raw`，
也不得从数组中删除元素。

**契约 C2**：`activeId` 指向的版本即「当前最新结果」，下一轮必须基于它，
而不是基于首轮原文。

---

## 2. 状态机

```
idle ──开始多轮──▶ running ──成功──▶ awaiting
                     │                  │
                     │                  ├─选方向──▶ running（基于 cursorId 那一版）
                     │                  ├─改文本──▶ awaiting（原地更新 edited）
                     │                  ├─回退──────▶ awaiting（只改 cursorId）
                     │                  ├─加入输入框──▶ awaiting
                     │                  └─结束多轮──▶ idle
                     └──失败──▶ failed ──重试──▶ running
```

**契约 C3**：`awaiting` 是唯一允许用户选择方向和回退的阶段。`running` 期间
方向按钮与回退按钮都必须禁用，避免并发发起下一轮。

**契约 C4**：`failed` 必须保留失败前最后成功的版本，不得清空历史。

---

## 3. 每轮界面结构

自上而下，顺序固定：

```
┌─────────────────────────────────────────────┐
│ 第 N 轮优化      基于 v2 ▸ 历史(5) ▸ 回退中  │  ← 轮次条
├─────────────────────────────────────────────┤
│ ┌─────────────────────────────────────────┐ │
│ │ 可编辑区域（textarea）                   │ │  ← 必须可编辑
│ │ 本轮优化后的提示词…                      │ │
│ └─────────────────────────────────────────┘ │
│ 已编辑 · 128 字                              │
├─────────────────────────────────────────────┤
│ 继续优化方向                                 │
│  1. 补充约束条件：明确每次输出的字数上限     │
│  2. 调整输出格式：改为三段式并带小标题       │
│  3. 增强角色设定：指定领域专家身份与口吻     │
├─────────────────────────────────────────────┤
│ [ 替换输入框 ]  [ 复制 ]  [ 结束多轮 ]        │
└─────────────────────────────────────────────┘

展开历史时，在轮次条下方插入：

┌─────────────────────────────────────────────┐
│ 历史版本                                     │
│ ┃ v5  第5轮  基于 v2  「增强角色设定」 210字 │
│ ┃     ▸ 展开                                 │
│ ┃ v4  第4轮  基于 v3  「调整输出格式」 186字 │  ← 分叉，缩进
│ ┃ v3  第3轮  基于 v2  「补充约束条件」 170字 │
│ ┃ v2  第2轮  基于 v1  「细化成功标准」 152字 │  ◀ 当前
│ ┃ v1  第1轮  初始         —              98字 │
│ │  [ 回退到这一版 ]                          │
└─────────────────────────────────────────────┘
```

**契约 C5**：三段内容缺一不可——结果、3 个方向、操作入口。

**契约 C6**：轮次条必须同时表达「第几轮」和「基于哪一版」，
回退状态下还要显示「回退中」，避免用户误以为自己仍站在最新版上。

## 4. 方向生成规则

方向不是候选答案，而是**下一步怎么做**的指令。

**契约 C7**：每个方向必须包含两部分——**动作 + 目标**，例如
「补充约束条件：明确每次输出不超过 300 字」。

**契约 C8**：3 个方向必须落在不同维度，禁止同义改写。
推荐维度池（每次从中取 3 个不同项）：

| 维度 | 示例 |
| --- | --- |
| 约束条件 | 明确长度、时间范围、禁用项 |
| 输出格式 | 改为表格 / JSON / 三段式 |
| 角色设定 | 指定专家身份、语气、受众 |
| 成功标准 | 给出可验证的验收条件 |
| 输入处理 | 明确缺失信息时如何处理 |
| 边界情况 | 补充异常输入、空值、超长文本的处理 |

**契约 C9**：方向必须与当前结果相关。判定方法：方向文案禁止出现
与结果无关的通用套话（如「让它更好」）；每个方向应能对应到
结果中确实缺失或薄弱的一环。

**契约 C10**：方向文案长度 ≤ 40 字，单句，不带编号（编号由界面渲染）。

**契约 C11**：方向生成失败时，必须回落到本地兜底方向
（补充约束条件 / 调整输出格式 / 细化成功标准），不得让流程卡死。

---

## 5. 选择方向的执行规则

**契约 C12**：用户点击方向后，新一轮的输入基线是 `cursorId` 指向版本的
`edited`，**不是** `raw`，也不是「最后一个版本」。

理由：用户可能已手动改进过文本，也可能已回退到某一版；继续优化必须接着
**用户当前选中的那一版**走。

**契约 C13**：发起新一轮时，把所选方向作为附加指令拼进系统提示词，
格式固定为：

```
Continue improving the prompt below in exactly this direction:
<方向文案>

Rules:
- Build on the current text; do not discard content it already establishes.
- Return only the improved prompt text.
```

**契约 C14**：新一轮产生新版本，`baseId` 指向基线版本，`direction` 记录所选方向。
旧版本原样保留。

**契约 C15**：禁止任何「回退即删除」的行为。回退只改变 `cursorId`，
`versions` 数组的长度和内容都不变。

## 5.5 历史与回退

### 5.5.1 历史面板

**契约 C21**：历史面板列出全部版本，按 v1→vN 顺序，每条显示：
版本号、轮次、基于哪一版、触发方向（首轮显示「初始」）、字数、
创建时间、以及是否为当前基线。

**契约 C22**：当前基线必须有明显标记（如左侧竖条 + 「当前」徽标），
让用户一眼看出自己站在哪一版上。

**契约 C23**：历史面板中每条可以单独折叠预览，默认只显示前 2 行，
点击展开完整内容。

### 5.5.2 回退行为

**契约 C24**：点击某条历史的「回退到此版本」，执行：

1. `cursorId = 该版本 id`
2. 该版本的 `edited` 载入结果编辑区，可继续编辑
3. 之后选方向发起的新一轮，基线是该版本
4. **不删除任何版本**

**契约 C25**：回退不改变 `versions` 数组，因此历史面板条目数不变。

**契约 C26**：回退后若再发起优化，产生的新版本 `rolledBackFrom` 记录
回退起点、`baseId` 记录实际基线。两者在正常顺延时相等；
若用户从 v2 回退后连续优化两次，则 v4 的 `baseId` 是 v3，
而 v3 的 `rolledBackFrom` 是 v2。

**契约 C27**：回退是**视图切换**，不是破坏性操作，因此不需要二次确认。
但若当前活跃版本有未保存的编辑，回退前需提示（可选：自动保存编辑）。

**契约 C28**：回退后，之前「未来」的版本仍然可见、可再次回退过去，
表现为一条分叉但都保留的链：

```
v1 ──▶ v2 ──▶ v3 ──▶ v4
        ▲
        └── 回退到 v2 后从这里继续，产生 v5
                         v5.baseId = v2
```

**契约 C29**：历史面板中因回退产生的分叉，用缩进或连接线表达父子关系，
不能只是平铺列表让用户自己数。

### 5.5.3 临时保存

**契约 C30**：多轮会话状态在**会话存续期内**保存在内存，切换会话面板
再回来，历史仍在。

**契约 C31**：可选持久化到 `sessionStorage`，key 为
`dsh-prompt-scatter:multiround:<sessionId>`，让刷新页面后历史不丢。
**不写入 `localStorage`**——避免跨会话串台。

**契约 C32**：会话关闭时清理对应的 `sessionStorage` 条目。

## 6. 编辑与加入输入框

**契约 C16**：结果区必须是真正的可编辑控件（`textarea` 或
`contenteditable`），不是只读文本。

**契约 C17**：编辑必须即时写回 `activeVersion.edited`。
切换轮次或关闭面板后重新打开，编辑内容不得丢失。

**契约 C18**：「加入输入框」写入的内容必须是 `edited`，
**不是** `raw`。这是本需求最容易实现错的一条。

**契约 C19**：写入方式需明确且可预期。默认行为：**替换**输入框现有内容；
若输入框非空，必须在按钮上给出提示（如「替换输入框」而非「加入输入框」），
避免用户误以为会追加。

**契约 C20**：写入后不自动发送，不关闭多轮会话，用户可继续优化。

**建议 S1**：提供第二种写入方式（插入到光标处 / 追加到末尾），
用同一个按钮的第二个入口承载，默认仍是替换。

## 7. 边界情况

| 情况 | 必须的行为 |
| --- | --- |
| 首轮时输入框为空 | 阻止发起，提示「请先输入要优化的提示词」 |
| 模型调用失败 | 进入 `failed`，保留历史，提供重试 |
| 用户在 `running` 中关闭面板 | 中止请求；已完成的历史保留 |
| 方向生成失败 | 回落兜底方向（C11） |
| 用户编辑到空内容 | 「加入输入框」禁用，避免写入空字符串 |
| 连续快速点击方向 | 第二次点击忽略（C3） |
| 结果超长 | 编辑区可滚动，高度上限 50vh |
| 切换会话 | 多轮状态按会话隔离，不串台 |
| 回退到当前正在编辑的版本 | 忽略（无变化） |
| `running` 中点回退 | 按钮禁用，无法触发 |
| 回退后再选方向继续 | 新版本从回退点分出，旧的前向版本保留 |
| 历史版本很多（>20） | 历史面板内部滚动，不撑高主面板 |
| 刷新页面后回来 | 有 `sessionStorage` 则恢复，否则回到 idle |

## 8. 验收标准

实现完成后，下列每条都可直接手动验证：

| 编号 | 验收项 |
| --- | --- |
| A1 | 开启多轮后，每轮输出同时包含：结果、3 个方向、操作入口 |
| A2 | 3 个方向互不重复，且都能一句话说清目标 |
| A3 | 选择方向后，第 2 轮结果明显承接第 1 轮，而非重新开始 |
| A4 | 第 2 轮完成后，历史里第 1 轮仍然存在且内容未变 |
| A5 | 轮次条显示「第 N 轮 · 基于 vN」 |
| A6 | 结果区可直接编辑，输入有响应 |
| A7 | 编辑后点击「加入输入框」，输入框内容等于编辑后的文本 |
| A8 | 编辑后刷新/重开面板，编辑内容仍在 |
| A9 | `running` 期间方向按钮不可点 |
| A10 | 模型失败后历史保留，可重试 |
| A11 | 空草稿时无法开始多轮 |
| A12 | 连续 5 轮后，历史中 5 个版本齐全、顺序正确、不可删除 |
| A13 | 历史面板打开后能看到全部版本，当前版本有标记 |
| A14 | 点「回退到 v2」后，编辑区内容变为 v2 的内容 |
| A15 | 回退后历史条目数不变（回退不删版本） |
| A16 | 回退到 v2 再优化，新版本 `baseId` 是 v2，轮次条显示基于 v2 |
| A17 | 回退产生的分叉在原版本之后继续，旧版本仍可再次回退 |
| A18 | 切换会话再回来，多轮历史仍在（内存级） |
| A19 | 刷新页面后，若启用 `sessionStorage` 持久化，历史可恢复 |
| A20 | 回退状态下轮次条显示「回退中」提示 |

## 9. 非目标

明确不做，避免范围蔓延：

- 不做多版本并行对比（那是「候选模式」，与本模式的语义不同）
- 不做跨会话的持久化历史（`sessionStorage` 仅限当前会话）
- 不做自动连续优化（每一轮必须由用户选方向驱动）
- 不做「回退即删除」——回退只切换基线，版本链永远保留
- 不做版本合并/差异对比（diff 视图超出本轮范围）

---

## 10. 与当前实现的差距

现有代码里，多轮模式是「一次并行生成 3 个候选答案」，与本文档要求
的「一轮一个结果 + 3 个继续方向」是两种不同的产品形态：

| 能力 | 当前实现 | 本规范要求 |
| --- | --- | --- |
| 一轮产出 | 3 个候选（均衡/精简/详尽） | 1 个结果 + 3 个方向 |
| 方向来源 | 预先写死的风格变体 | 依据当前结果动态生成 |
| 历史 | 只有「原话」+ 当前轮候选 | 完整版本链 v1..vN，只追加 |
| 结果可编辑 | 只读 div | 必须可编辑 |
| 加入输入框 | 替换草稿 | 替换（并明确提示）或插入 |
| 轮次表达 | 有轮次数字 | 轮次 + 基线版本 |
| 回退 | 无 | 可回退到任意历史版本，不删版本 |
| 临时保存 | 无 | 内存 + 可选 sessionStorage |

结论：需要重写多轮流程，而不是在现有候选模式上打补丁。
`lib/probe.js`、`lib/config.js`、单轮预览与写回逻辑可原样复用。
